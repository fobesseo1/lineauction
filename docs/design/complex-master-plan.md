# 수도권 아파트·오피스텔 단지 목록(단지 마스터) 구축 계획

작성일: 2026-10-11. 데이터 공장(이 저장소) 작업이다. lineestate 서비스는 이 결과를 `public` 스키마에서 읽기만 한다.

## 원칙

- **공공 원천만 쓴다.** 아실 등 경쟁 서비스 크롤링 금지. 아실은 사람이 몇 개 단지를 열어 결과를 대조하는 검증용으로만 쓴다.
- 범위: 서울·경기·인천의 아파트와 오피스텔. 빌라는 1.5단계에 같은 구조로 확장한다.
- 원본 저장 → 정규화 → 매칭 → 검수 순서를 분리한다. 계약일과 수집일은 따로 저장한다.

### 좌표 원천 주의

- 브이월드 지오코더는 지침상 **결과를 DB에 저장하지 말고 실시간으로만 쓰라**고 되어 있다. 단지 좌표를 저장해야 하므로 기본 원천으로 쓰지 않는다.
- 후보 1: 행정안전부 주소정보(juso.go.kr)의 좌표 제공 API, 또는 위치정보요약 DB 파일. 이용 조건을 확인한 뒤 결정한다.
- 후보 2: 건축물대장 지번 → 필지 중심점(연속지적도). 나중에 상가·토지 단계에서도 필요하다.

## 단계

### 1. 단지 목록 (K-APT)
- 수도권 시군구마다 `getSigunguAptList4`를 호출해 `kaptCode`, 단지명, 법정동코드를 받는다.
- K-APT는 의무관리 대상 단지 위주라서 **소형 단지와 오피스텔이 빠진다.** 이 부분은 3단계에서 채운다.

### 2. 단지 기본정보
- `kaptCode`마다 기본(`getAphusBassInfoV5`)과 상세(`getAphusDtlInfoV5`)를 호출한다.
- 개발 한도가 하루 5,000건이라 며칠에 나눠 받는다. 운영계정 증설(활용사례 등록)을 신청하면 빨라진다.
- 법정동주소에서 **법정동코드 + 본번 + 부번**을 뽑아 매칭 키로 쓴다.

### 3. 실거래 전체 수집 (수도권, 아파트·오피스텔, 매매·전월세)
- 지금은 경매 물건에 매칭된 실거래만 갖고 있다. 이제 **수도권 전체 실거래**를 쌓는다.
- 호출 규모 (예: 2016~2026, 약 120개월): 시군구 약 77개 × 120개월 ≈ API당 약 9,200회. 하루 10,000 한도면 API당 하루~이틀이 걸린다.
- 매일: 최근 3개월을 다시 조회해 취소(해제)·정정을 반영한다.
- 실거래에 있는데 K-APT 목록에 없는 단지(소형 단지, 오피스텔)는 **실거래의 지번으로 건축물대장 표제부를 조회해** 단지 목록에 추가한다.

### 4. 매칭: 실거래 ↔ 단지
- 1차 키: 법정동코드 + 지번 (본번·부번)
- 보조: 단지명 유사도, 건축연도(사용승인일), 전용면적
- 애매한 건은 **수동 검수 대기열**로 보낸다. 다른 단지에 거래가 잘못 붙는 것을 가장 먼저 막는다.

### 5. 면적 타입
- 실거래의 전용면적 목록, K-APT의 전용면적별 세대현황, 건축물대장 전유부를 묶어 단지별 평형 목록을 만든다.
- 공급면적과 전용면적은 구분해 저장한다. 비슷한 면적을 임의로 합치지 않는다.

### 6. 좌표
- 위 "좌표 원천 주의"에서 결정한 원천으로 단지 대표 좌표를 채운다.

### 7. 검증
- 아실 조사 자료에 나온 단지(헬리오시티, 은마, 도곡렉슬 등)로 세대수, 사용승인일, 평형 목록, 최근 실거래를 사람이 대조한다.
- 매칭률을 집계한다: 실거래 중 단지에 붙은 비율, 수동 검수 건수.

## 데이터 모델 (`public` 스키마, 초안)

| 테이블 | 핵심 칸 |
|---|---|
| `complexes` | id, 섹션(apartment), 유형(아파트/오피스텔), 대표명, 법정동코드, 본번, 부번, 도로명주소, 좌표, 세대수, 동수, 사용승인일, 용적률, 건폐율, 시공사, 난방, 주차 |
| `complex_source_ids` | complex_id, 원천(kapt/건축물대장/부동산원), 원천 ID, 매칭 신뢰도 |
| `complex_aliases` | complex_id, 별칭(실거래 단지명, 옛 이름) |
| `complex_area_types` | complex_id, 전용㎡, 공급㎡, 세대수, 원천 |
| `market_transactions` | 원천 원본 키, complex_id, 매매/전세/월세, 계약일, 금액, 보증금, 월세, 층, 동, 전용㎡, 직거래 여부, 해제일, 최초 수집일 |
| `complex_match_queue` | 매칭이 애매한 실거래, 후보 단지, 처리 상태 |

기존 경매 물건(`properties`)은 `complex_id`로 단지에 연결한다. 기존 `transactions` 테이블과의 관계는 구현할 때 정리한다.

## lineestate와의 관계

- lineestate는 단지 테이블을 **직접 만들지 않는다.** 이 저장소가 만든 `public` 테이블을 읽는다.
- 화면 개발은 실데이터가 들어오기 전에도 진행할 수 있다. 테이블 구조가 확정되면 lineestate에 알린다.
