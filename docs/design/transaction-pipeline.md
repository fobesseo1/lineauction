# 실거래 수집·공매 비교 설계 초안

2026-10-06의 실제 응답 6종을 기반으로 한 제안입니다. 구현·DB 변경 전 검토용 문서입니다. 원시 응답은 `docs/samples/2026-10-06/review.md`를 참조합니다.

## 데이터 의미

- 국토부 dealAmount는 만원 단위입니다. 쉼표 제거 후 BigInt로 10,000을 곱하고 원 단위 문자열로 저장합니다. 예: `203,500` → `2035000000`원. 온비드 금액은 기존 어댑터의 원 단위 처리를 유지합니다.
- 지역 코드는 숫자가 아닌 문자열로 보존합니다. API의 sggCd는 시군구 코드이며, 중개사 소재지 estateAgentSggNm을 물건 주소로 쓰지 않습니다.
- 빈 값은 null로 정규화합니다. 지번의 별표는 유지하며 주소 매칭에서 완전한 지번으로 취급하지 않습니다.
- 아파트·오피스텔·연립다세대는 excluUseAr(전용), 상업업무용은 buildingAr(건물), 토지는 dealArea(거래), 단독다가구는 totalFloorAr(연면적)와 plottageAr(대지)를 각각 보존합니다. 한 area 필드로 의미를 섞지 않습니다.
- 계약 해제 표시와 해제 날짜를 별도로 보존하고 비교 대상에서 제외합니다. 해제일은 날짜이므로 시간대가 있는 timestamp보다 date가 적절합니다.
- 건물 유형·용도, 지목·용도지역, 지분 거래, 토지임대부, 중개/직거래 여부를 보존합니다. 이번 토지 표본은 도로 지분 거래이므로 일반 토지와 섞지 않습니다.

## 함수 경계 제안

```ts
type TradeType =
  | "apartment" | "officetel" | "commercial"
  | "land" | "rowhouse" | "detached";

fetchTradePage({ type, regionCode, contractMonth, pageNo, pageSize });
parseTradeEnvelope(xml);             // 원문 → 헤더·페이지·문자열 행
validateTradeRow(type, row);         // 유형별 필수 필드 검증
normalizeTrade(type, row, context);  // 가격·날짜·면적 의미 통일
collectTradeMonth(type, regionCode, contractMonth);

findComparableTrades(property, policy);

```

API 클라이언트는 서버 전용이며 인증키를 URL 로그나 오류에 포함하지 않습니다. 서비스 레지스트리에 검증한 공식 endpoint와 유형별 스키마를 둡니다. XML 숫자 자동 변환을 끄고 1행/배열/빈 items를 같은 배열 형태로 처리합니다. HTTP 성공과 resultCode 성공을 각각 확인합니다. 인증·권한·잘못된 요청은 즉시 실패시키고 시간 초과·429·일시적 서버 오류만 제한적으로 재시도합니다.

## 수집과 변경 처리

시군구 × 계약월 × 유형 단위로 수집합니다. 페이지를 모두 받은 후 전체 건수와 검증 실패를 확인하고, 불완전하면 기존 월 데이터를 교체하지 않습니다. 수집 중 전체 건수가 변하면 해당 스냅샷을 다시 확인합니다. 신규 신고·정정·해제가 들어오므로 최근 계약월은 반복 조회하고 이전 월도 주기적으로 재확인합니다.

이번 표본 응답에는 안정적인 거래 고유 ID가 없습니다. 단지명·면적·층·계약일·가격이 같다는 이유만으로 중복 제거하면 서로 다른 거래를 잃을 수 있습니다. 월별 원문 스냅샷, 행 fingerprint와 동일 행의 발생 횟수를 보존하고 완전한 스냅샷만 교체하는 방식이 필요합니다. 정정된 거래의 같은 거래 여부는 API 필드만으로 단정하지 않습니다. 원문 보관 기간·조회 주기·예산은 구현 전에 설정값으로 결정합니다.

## 비교 방식 초안

1. 공매 물건의 유형, 실제 면적 종류, 주소와 지분 여부를 확인합니다. 거래가와 최저입찰가가 같은 권리·면적 범위를 가리키는지 확인하지 못하면 비교를 보류합니다.
2. 아파트·오피스텔은 같은 시군구·법정동·단지와 유사 전용면적을 우선합니다. 연립다세대는 같은 건물 식별 가능 여부를 먼저 확인합니다. 이름 정규화만으로 같은 건물이라고 확정하지 않습니다.
3. 비교 기간·면적 허용 범위·최소 표본 수는 설정값으로 둡니다. 해제 거래를 제외하고 층·건축연도 차이를 기록합니다. 직거래는 별도 표시하거나 설정에 따라 제외합니다.
4. 상업업무용은 집합/일반 건물과 용도, 면적 기준을 나눕니다. 단독다가구는 대지와 연면적을 모두 고려합니다. 토지는 지목·용도지역·지분 여부를 나눕니다. 이 유형들은 넓은 지역의 단순 평균으로 시세를 확정하지 않습니다.
5. 주거 동일 단지의 충분한 표본부터 중앙값과 ㎡당 가격 분포를 계산합니다. 면적이 다른 물건의 면적 환산 추정은 방법을 따로 표시합니다. 상업·토지·단독은 특성 차이를 반영할 근거가 없으면 추정값을 비워 둡니다.
6. 비교 가격뿐 아니라 표본 수, 기간, 매칭 단계, 제외 사유, 추정 범위를 반환합니다. 불충분하면 marketPrice=null 및 이유를 반환합니다. 등급을 억지로 생성하지 않습니다.

최저입찰가와 시세의 차이는 `가격 차이`이며 확정 수익이 아닙니다. 권리·점유·세금·비용 정보가 없는 상태에서는 profitability 점수를 만들 수 없으므로 현재 예약된 수익성 가중치 정책도 별도 결정이 필요합니다.

## 기존 모델에서 바꿀 점

현재 Transaction.property_type에는 apartment/officetel/commercial/land만 있으므로 rowhouse와 detached를 추가해야 합니다. area 하나 대신 면적별 값과 비교 기준을 추가하고, build_year·취소 여부·지분·지목·용도·원문/스냅샷 메타데이터를 보존해야 합니다. transactions.property_id 하나로 비교 대상을 연결하면 여러 공매 물건에서 같은 거래를 재사용하기 어렵습니다. 거래 데이터는 독립적으로 저장하고 비교 결과에서 거래 ID 목록과 매칭 근거를 연결하는 편이 적합합니다.

## 구현 순서와 검증

먼저 6종 파서·정규화와 실제 응답 fixture 테스트를 구현한 후 월별 수집을 연결합니다. 공통 수집은 6종을 지원하되 가격 비교는 동일 단지 아파트부터 검증하고 유형별 매칭을 확장합니다. 의미 있는 테스트는 만원→원 변환, 빈 면적, 가려진 지번, 지분·취소 제외, 동일 필드의 복수 거래 보존, 페이지 중간 실패 시 기존 데이터 유지, 표본 부족 시 추정 보류입니다.
