# 법원 수집 → DB → 실거래 → 화면 실행

**현재 범위 변경(2026-10-07): [서울·경기 우선 계획](seoul-gyeonggi-roadmap.md)이 아래 전국 순회 설명보다 우선한다.** 서울·경기 주소 물건의 상세·사진 → 상태 → 실거래 → 화면 순서로 진행한다. 기본 `queue`와 파이프라인은 서울·경기만 처리하며 기존 전국 DB 자료는 보존한다. 전국 목록 추가 순회는 보류한다. 상세는 `detail-batch.mjs`로 사진까지 함께 수집하고, 물건 위치가 바뀐 경우에만 해당 법원 목록을 갱신한다. 검증된 비교 지역에는 기존 서울중앙 6개 구 외 고양 일산동구·일산서구가 추가되었다.

## 예약 작업에서 수행할 절차

1. 이 폴더에서 `npm run court:plan`. 다음 법원·시작 페이지를 얻는다. `needsFinalize`면 `node scripts/court/plan.mjs "법원명" --finalize`를 먼저 실행한다.
2. `npm run court:receive`로 로컬 수신기를 시작한다. 이미 실행 중이면 기존 수신기를 사용한다.
3. CUA로 공식 `https://www.courtauction.go.kr` 홈페이지를 연다. 법원 기본 선택 요소 `#mf_sbx_rletRpdtCortLst`의 **화면에 실제 존재하는** 옵션을 `selectOption({label:court})`로 선택하고 `검색하기`를 누른다. 최초 DOM에서 이 선택 요소·버튼이 실제 있는지 확인한다. 법원 목록이 달라졌으면 `scripts/court/courts.json`과 비교하고 변경을 보고한다.
4. 조회 조건에 해당 법원이 나타났는지 기다린 뒤, 결과가 있으면 `페이지당 수 선택`을 40으로 선택한다. 0건은 페이지 크기 선택 요소가 없다. `scripts/court/list-batch.mjs`의 함수를 CUA에 함수 리터럴로 정의한다. eval/동적 스크립트 로딩/별도 Playwright 실행 금지. `collectCourtListBatch(tab,court,startPage,15)`를 실행하고 `run.pageSize=40`을 기록한다. 과거 10건 페이지와 섞지 않는다. 각 호출은 60초 이내로 나눈다. 함수는 목록 두 번의 안정된 DOM과 마지막 페이지 하한을 확인하며, 검증 실패 시 원인을 해결하고 다시 조회한다.
5. CUA에서 `http://127.0.0.1:3001` 수신기 입력란 `수집 원문 JSON`에 결과 JSON을 채우고 `검증하고 저장`을 클릭한다. `수집 저장 완료`를 확인한다. 사람에게 복사를 요구하지 않는다. 다음 저장은 `다음 수집` 링크를 이용한다.
6. 마지막 페이지에 도달하면 `node scripts/court/plan.mjs "법원명" --finalize`. 같은 날의 페이지 원문을 합쳐 **전체 페이지·고유 물건수·화면 총수**가 일치하는지 검증한다. 부분 수집은 종결/취하로 해석하지 않는다. 마지막까지 도달했어도 검증이 실패하면 해당 법원을 완료로 세지 않는다.
7. `npm run court:plan`으로 다음 법원. 약 10분에서 목록 순회를 멈추고 남은 약 10분은 상세에 사용한다. 상세 대기열은 `node scripts/court/cli.mjs queue`; `scripts/court/browser.mjs`의 기존 `collectCourtPages` 함수로 법원·페이지·onlyDetailKeys를 지정해 한 호출 최대 4건씩 처리하고 같은 수신기로 저장한다. 다음 큐를 다시 읽어 여러 배치를 반복한다. 큐의 해당 법원 기본 검색을 먼저 열어야 한다. 목록 수집을 모두 끝낼 때까지 상세 처리를 무기한 미루지 말고 매 실행에서 최소 한 배치를 수행한다.
8. `npm run court:pipeline`으로 실제 Supabase 저장과 국토부 재조회를 실행한다. 서버 키는 `.env.local`에서만 읽고 출력하지 않는다. 동시 실행은 로컬 lock 파일로 막는다. 강제 종료 시 lock을 자동 삭제하지 말고 기존 프로세스가 종료됐는지 확인한 후 복구한다.
9. `data/court/pipeline/latest.json`과 Supabase `collection_runs`를 확인한다. 오류가 있으면 `completed`로 보고하지 않는다. `http://127.0.0.1:3000/properties?demo=0`과 보고서의 예시 상세 URL을 CUA로 열어 실제 자료 표시를 확인한다. 로컬 앱이 꺼져 있으면 `npm run dev`를 시작한다. 화면은 요청 시 DB를 읽는다. 이미 열린 화면은 새로고침해야 한다.
10. 이번에 시작한 임시 수신기는 종료한다. 의미 있는 데이터 변경·실패·사용자 조치가 필요할 때만 알리고, 변화가 없으면 조용히 종료한다.

## 저장과 비교 규칙

- `properties`: 기존 RPC로 법원+사건번호+물건번호를 식별. 신규/변경/동일/역순 관측을 분리. 가격·상태 변경 이력은 기존 DB 트리거 사용.
- `court_observations`: 원문 및 자산 목록·관측 시각. 비공개 서버 전용.
- `collection_runs`: DB 처리 실행 기록. 비공개 서버 전용. 브라우저 수집 실행의 상세 범위·원문은 로컬 `data/court/runs`에 별도로 보존한다.
- `property_comparisons`: 공개 가능한 비교 스냅샷. 검증된 거래 목록과 출처/기간/규칙/미매칭 사유. 거래가 아니라 추정시세를 만드는 기능은 없다.
- `transactions`: 비교에 채택한 국토부 거래를 내용 해시로 중복 없이 저장. 조회 지역 전체 원문 XML은 로컬 저장. 해제·다른 면적 거래는 비교 결과에 채택하지 않는다.

현재 검증한 규칙은 아파트 전용이다. 법원 상세의 전유면적, 목록의 단지명·법정동, 상세 지번이 있어야 한다. 현재 법정동 코드 지원은 서울중앙 관할 6개 구이며, 다른 지역은 매칭 전 단계로 남는다. 같은 단지·동네·지번 및 면적 차이 0.1㎡ 이하, 현재 월 포함 최근 6개월, 해제 거래 제외. 같은 동은 강제하지 않고 층/동 차이를 공개한다. 0.1㎡ 기준은 1차 검증 규칙이며 더 넓은 유사면적 규칙은 별도 검증 후 도입한다.

일반 주택/상가/토지의 인근 비교, 전국 법정동 코드 확장, 권리분석, 문서 수집은 구현 완료로 표시하지 않는다. 수집된 자료가 없어진 것만으로 매각/취하 상태를 만들지 않는다. 비교 조회가 실패하면 이전 스냅샷의 확인시각을 유지하고 실행 오류로 기록한다.

## 사진과 상태 갱신 (2026-10-07 추가)

- 상세 배치에서 방문한 물건은 공개 사진을 함께 저장한다. CUA에서 보이는 `전경도_N`, `관련사진_N` 이미지의 `src`를 DOM으로 읽는다. 긴 data URL은 반환 시 잘릴 수 있으므로 `src.match(/.{1,24000}/g)` 배열로 나눠 읽고 CUA 런타임에서 합친다. `[Truncated]`가 포함된 데이터는 절대 저장하지 않는다.
- 수신기에 `{kind:'court-media',key,court,caseNumber,itemNumber,sourceUrl,observedAt,detailRaw,photos:[{alt,dataUrl}]}`를 입력한다. `detailRaw`는 현재 화면의 보이는 상세 표 텍스트다. 서버에서 사건·물건번호를 다시 검증하고 Sharp로 최대 640×480, 품질 60 WebP로 변환한다. 파일은 `public/media/court`, 출처/용량/크기는 `data/court/media/manifest.json`과 DB `property_media`에 저장한다. 현재는 이 PC의 공개 폴더를 사용하므로 배포 시 해당 사진 파일도 포함해야 한다.
- 전체 목록 검증 때만 미관측 물건을 `needs-recheck`로 기록한다. 부분 수집/오류/단순 날짜 경과로 종료 처리하지 않는다. 목록에 다시 관측되면 재확인 상태를 해제한다.
- 상태 재확인 배치는 공식 `매각결과검색` 화면을 이용한다. 법원을 선택하고 검색한다. 이 화면은 매각기일 다음 날부터 7일간 결과를 제공하므로 매일 확인한다. 오래된 미관측 물건은 `경매사건검색`의 기일내역 확인 대상으로 남기며, 그 파서는 아직 구현 전이다.
- 결과 표의 보이는 `tbody tr` → `td.innerText` 배열과 검색조건 텍스트를 수신기에 `{kind:'court-results',court,query,sourceUrl,observedAt,rows}`로 저장한다. 사건·물건번호가 있는 7칸 행과 바로 뒤 3칸 결과 행을 검증한다. 일괄매각의 빈 식별자 후속행은 새 결과로 만들지 않는다. 새 기일보다 오래된 매각 결과는 종료 근거로 사용하지 않는다.
- 명시적인 `매각`은 **해당 입찰 종료·대금납부 미확인**으로 표시한다. `유찰`은 종료로 만들지 않는다. 취하/취소/납부완료를 임의 추론하지 않는다. 근거 원문은 `data/court/results`와 상태 증거에 남긴다.
- DB `property_lifecycle`과 변경 이력 테이블은 가격 이력과 별개다. 기본 목록은 종료 확인 물건을 제외하며 `종료 확인 물건`/`전체 이력 포함` 필터로 다시 조회한다. 상세에는 상태·확인시각·변경 이력과 실제 사진 출처를 표시한다.
- 매 예약 실행에서 목록/상세 시간 일부를 결과 재확인에 배정한다. 수집 후 `npm run court:pipeline`은 묶음 RPC로 저장하고, 사진·상태·비교를 연결한다. 단계 오류는 실행 보고서에 남긴다. 전국 전체 페이지 검증과 일부 페이지만 저장한 법원 수를 구분해서 보고한다.
- 사진·결과 표 수집 함수는 `scripts/court/browser-evidence.mjs`에 있다. CUA에 함수 리터럴로 정의한 뒤 `collectCourtPhotos(tab,item)` 또는 `collectCourtResultPage(tab,court)`를 실행한다. 결과를 로컬 수신기에 저장한다. 사진이 없으면 null이므로 사진 저장을 건너뛴다.
- 여러 법원의 마지막 페이지까지 저장했다면 `node scripts/court/finalize.mjs`로 전체 병합 검증을 한 번에 수행할 수 있다. `data/court/finalization.json`의 errors가 없어야 한다. `node scripts/court/coverage.mjs`로 전체/부분/미조회 범위를 확인한다. 최종 병합과 브라우저 저장은 동시에 실행하지 않는다.

추가 스키마 원본: `scripts/court/lifecycle-schema.sql`. 적용 마이그레이션: `court_lifecycle_media_and_batch`, `court_catalog_lifecycle_cover`.

초기 DB 연결 첫 실행에서 날짜만 있는 법원 매각기일을 00:00 KST의 입찰마감으로 넣은 오류가 있었다. 매퍼를 null로 수정하고 재실행하여 현재 물건 값은 바로잡았다. 기존 가격 이력의 원본은 보존한다. 법원 이력의 마감 시각은 화면에서 모두 미확인으로 표시하며, 이력의 초기 자정값을 실제 마감시각으로 사용하지 않는다. 이력 일괄 수정 SQL은 자동 승인 검토에서 거절되어 실행하지 않았다.

## 검증 기준

`npm run court:test`, `npm test`, `npm run typecheck`, `npm run lint`.
DB에서 source별 개수, 중복키, 실행 결과, 거래 개수와 RLS 권한을 확인한다. 동일 원문 재실행 시 물건·거래 행수와 가격 이력이 불필요하게 증가하지 않아야 한다.

추가 스키마 원본은 `scripts/court/pipeline-schema.sql`이며 Supabase MCP의 `court_collection_pipeline` 마이그레이션으로 적용했다. CLI가 이 환경에 없어 로컬 migration 파일명을 임의 생성하지 않았다.
