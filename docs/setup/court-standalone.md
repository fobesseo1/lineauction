# 독립 최초 수집기

2026-10-08 사용자 지시: PC를 켜 둔 상태에서 대화와 별개로 동작하는 수집기를 만들고 시험한다. 매일 09시 예약은 PAUSED로 유지한다. 이 문서의 수동 최초 수집 실행은 예약 갱신이 아니다.

## 방식과 범위

Node.js + Playwright Core가 별도 Edge headless 브라우저를 실행한다. 기존 사용자의 브라우저 프로필·로그인·쿠키는 읽지 않는다. 공개 화면의 선택·클릭·표 읽기만 사용하고 내부 HTTP 데이터 요청을 재현하지 않는다. 프록시·스텔스·보안 확인 우회를 사용하지 않는다.

서울·경기 관할 16개 법원/지원의 목록을 현재 공개 검색 조건으로 순회하며, 주소가 서울특별시·경기도인 부동산만 상세 보강한다. 인천 소재는 제외한다. 관할만으로 소재지를 추정하지 않는다. 현재 대표 공식 사진은 물건당 1장이다. 상세·사진 확보를 공식 종료 상태 확인이나 전체 0~3단계 완료로 표시하지 않는다.

약관 확인: 공식 홈페이지 하단 이용약관 제15조에는 동의 없는 서비스 내용 가공 및 입찰참가 외 영리 이용에 관한 제한이 있다. 공개된 HTTP 수집 허가 문서는 확인하지 못했다. 2026-10-08 `robots.txt` 조회는 404였으며, 이를 허가로 해석하지 않는다. 기술적 접속 성공은 이용 허가 확인과 다르다. 운영·재배포 조건은 별도 확인 사항으로 남긴다.

## 실행

대표 시험: `npm run court:collect -- --limit=20 --court=서울중앙지방법원`

대화 종료와 무관하게 최초 수집 실행: PowerShell에서 `./scripts/court/start-initial.ps1`. 숨김 프로세스로 실행하고 대기열 순회를 마치거나 차단·오류 조건에 도달하면 종료한다. 반복 예약을 만들지 않는다. PC 절전·종료 중에는 수집되지 않는다.

진행 확인: `npm run court:status`. 상세 기록은 `data/court/standalone/progress.json`, `events.jsonl`, 회차별 `run-*.json`, 실행 로그에 있다. process alive 확인은 PID 조회이므로 정확한 프로세스 정체는 운영체제에서 함께 확인한다.

중지: `data/court/standalone/STOP` 파일을 만든다. 현재 물건 처리 또는 동기화가 끝난 뒤 중지한다. 재개 시 중지 파일을 의도적으로 제거하고 다시 실행한다. 잠금 파일이 있으면 해당 PID의 종료 여부를 먼저 확인하며 무조건 삭제하지 않는다. 기존 CUA 수신기 수집과 동시에 실행하지 않는다.

## 저장·재개·속도

- 매 상세 건마다 기존 `saveRun`의 식별자 검증과 원자적 현재 파일 교체를 사용한다. 사진은 같은 프로세스에서 `saveMedia`로 WebP 저장하며 도구 간 조각 전송을 없앴다.
- 사진 성공 여부를 건별 기록한다. 다시 실행하면 이미 상세·사진 저장을 완료한 물건을 건너뛴다. 중간 페이지에서 멈추면 그 페이지를 다시 읽고 미완료 물건부터 이어간다.
- 페이지·검색 조건은 원문으로 재검증한다. 목록 로딩 틀과 실제 값 도착을 구별한다. 마지막 페이지는 표시된 페이지 버튼으로 확인한다.
- 화면에서 안 보였다는 이유로 매각·취하·취소를 만들지 않는다. 403/429 또는 접근 제한·보안 확인 시 우회 없이 중지한다. 연속 상세 실패 3회도 중지하고 근거를 남긴다.
- 숨김 최초 수집 실행은 100건마다 및 회차 종료 시 기존 DB·국토부 처리기를 실행한다. 동기화 중에는 수집이 기다리므로 현재 파일에 대한 동시 쓰기를 피한다. 동기화 실패는 수집 성공과 별도로 기록한다. 기존 실거래 매칭 규칙의 지원 범위는 확대하지 않았다.
- 단일 브라우저에서 순차 처리한다. 과도한 동시 접속으로 속도를 올리지 않는다. 실제 속도는 법원 로딩, 디스크 저장, 사진, 국토부 조회에 따라 달라진다.

## 수집 모니터링 · 2026-10-08

설정 페이지 `/settings`의 서울·경기 수집 현황 패널에서 확인한다. 별도 `scripts/court/monitor.mjs` 프로세스가 20초마다 PID 생존·진행 파일 갱신·최근 저장 성공·DB 결과를 확인하고, 전체 상세·사진 집계는 1분 간격으로 갱신한다. 화면은 10초마다 로컬 전용 `/api/court-monitor`를 조회한다. 원문·환경변수·비밀키·전체 로그는 이 API에 포함하지 않는다.

감시기를 처음 시작하려면 `./scripts/court/start-monitor.ps1`. 수집기를 재시작하거나 예약을 만드는 기능은 없다. 감시기와 수집기는 독립 프로세스다. 감시기는 수집기가 종료돼도 계속 상태를 관측한다. 감시기 PID는 `monitor.lock`에 기록한다. 잠금이 남아 있으면 실제 PID를 확인한 후 처리한다.

수집 프로세스가 살아 있어도 2분간 새 처리 기록이 없으면 지연 의심, DB 반영 중에는 15분을 기준으로 판단한다. 프로세스 종료·확인 권한 없음·명시적 오류·DB 반영 실패는 각각 구별한다. 감시 파일이 1분 이상 오래됐거나 브라우저 조회가 실패하면 정상 상태로 표시하지 않는다. 완료 건수는 상세·사진을 따로 표시하고, 수집 실행 종료를 전체 0~3단계 완료로 표시하지 않는다. 화면은 로컬 PC용이며 배포 서버에서 이 PC의 파일을 원격으로 읽지는 않는다.

오류·지연·권한 부족·정상 종료·DB 반영 실패 판정 테스트 5개 통과. 실제 수집 PID 6880 및 독립 감시 PID 22680의 생존과 현황 화면 수치를 확인했다. 이 PID는 현재 실행 이력이며 재실행하면 달라진다.

## 시험 결과

### 일시 오류 자동 복구

목록 내용 변경, 화면 응답 시간 초과, 목록 안정화 실패는 같은 법원의 검색을 새 브라우저 컨텍스트에서 다시 시작한다. 과거 화면의 행 번호를 재사용하지 않고 체크포인트 페이지를 다시 검증하며 저장 완료된 상세·사진은 건너뛴다. 복구 대기는 10초·30초·60초, 새 저장 성공 없이 연속 3회까지다. 저장에 성공하면 연속 실패 예산은 초기화하지만 한 법원 실행의 총 재시도는 12회까지 제한한다. 한도를 넘으면 기존 중단 및 Windows 알림을 사용한다. STOP 요청은 복구 대기 중에도 1초 간격으로 반영한다.

403/429, 접근 제한·보안 확인, 법원/물건 검증 불일치, 알 수 없는 구조는 자동 복구하지 않는다. 강제 종료된 프로세스 자체를 자동 실행하는 감독기는 아니며, 이번 최초 수집 안에서만 동작한다. 매일 9시 예약이나 반복 갱신과 무관하다. 화면은 복구 대기를 '자동 복구 중'으로 구분하고, 복구 중에도 2분간 진행 기록이 없으면 지연으로 표시한다.

목록 읽기는 브라우저의 관련 데이터 요청 완료와 행 안정화를 함께 확인한다. 실제 진단에서 목록과 무관한 홈페이지 연도별 통계 요청 `pgj111/selectRletYrDspslStats.on`이 오래 열린 채 남는 것을 확인해 목록 준비 조건에서 제외했다. 모든 요청의 403/429 감지는 그대로 유지한다. 목록 변경 시 전후 원문은 `standalone/list-change.json`, 안정화 실패 시 대기 요청은 `standalone/list-loading.json`에 진단용으로 남긴다.

실제 서울중앙 17페이지의 목록 변경 원인: 처음 읽은 80행과 상세 복귀 후 18행의 처음 18행은 같았다. WebSquare가 짧은 마지막 페이지에서 이전 결과 행을 숨겨 두는 탓에 숨겨진 행을 결과에 포함했던 것이다. 목록 원문 추출과 상세 클릭의 행 선택을 모두 `tbody tr:visible` 기준으로 맞춰 숨겨진 잔여 행을 읽지 않는다. 실제 가격·상태·물건 변경에 대한 재검증은 유지한다.

사용자 요청에 따라 이 대화에 '선경매 수집 오류 자동 점검·복구' 오류 감시를 5분 간격으로 연결했다(automation-2). 정상·복구 대기는 조용히 종료하고, 해결되지 않은 중단·지연을 조사·수정·검증 후 안전하게 재개한다. 접근 차단이나 STOP은 존중한다. 이는 Windows 알림 자체가 즉시 AI를 호출하는 기능이 아니라 Codex 앱이 오류 기록을 주기적으로 읽는 기능이다. PC와 Codex 앱이 켜져 있어야 하며 정상 상태의 반복 알림은 없다. 기존 오전 9시 갱신 예약(automation)은 PAUSED로 유지한다.

### Windows 오류 알림

독립 감시기는 수집 오류 중단·예상치 못한 종료·처리 지연·DB 반영 실패·실행 여부 확인 실패를 발견하면 Windows 기본 NotifyIcon 알림을 보낸다. 웹페이지가 닫혀 있어도 동작하며 클릭하면 로컬 설정 화면을 연다. 감시기 자체의 상태 파일 읽기 오류도 알린다. 다만 감시기 프로세스 자체가 종료되거나 PC가 꺼지면 알림을 보낼 수 없다. 매일 9시 예약은 계속 중지한다.

동일 실행의 같은 장애는 `notification-state.json`에 기록해 감시기를 재시작해도 중복 알리지 않는다. 정상 복구 후 같은 장애가 다시 발생하면 새로 알린다. 계속 진행되는 개별 물건 실패는 첫 발견 때 알리고 이후 증가는 5분 단위로 묶는다. 새로운 중단 장애는 이 대기시간과 관계없이 알린다. 알림 실행 실패는 1분 후 재시도한다.

Windows 기본 알림은 방해 금지나 OS 알림 설정에 따라 표시가 제한될 수 있다. 설정 화면은 단순 전송 성공과 Windows의 표시 이벤트 확인을 구별한다. 표시 이벤트는 사용자가 읽었다는 뜻이 아니다. PowerShell은 별도 설치나 실행 정책 변경 없이 기본 Windows Forms를 사용한다.

## 국토부 접근 제한 중지 · 2026-10-08

국토부 실거래 API가 HTTP 403/429를 반환하면 `data/court/pipeline/molit-access-paused.json`에 중지 사유를 기록한다. 다음 처리와 이후 동기화에서도 이 파일이 있으면 추가 국토부 HTTP 요청을 보내지 않는다. 자동 삭제나 시간 경과 재개는 없다. 제한 원인과 재개 가능 여부를 확인한 뒤에만 의도적으로 해제한다. 법원 상세·사진 수집 및 해당 DB 저장은 계속하며, 조회 실패 물건의 기존 실거래 비교 자료는 덮어쓰지 않는다. 따라서 중지 중에는 비교 자료의 확인시각이 갱신되지 않는다. `molit-access-gate.test.mjs`의 403/429 영속 중지와 503 구분 테스트 3개를 통과했다.

## DB 저장과 실거래 매칭 상태 분리 · 2026-10-08

설정 화면과 Windows 감시는 최근 파이프라인 오류의 단계를 구분한다. `matching` 단계만 실패한 경우 법원 물건·사진 DB 저장 오류로 표시하지 않고 '수집 중 · 실거래 매칭 보류'로 표시한다. DB 저장 단계 오류와 최신 저장 결과 미확인은 계속 경고한다. 오래된 성공 보고서가 최근 실패를 가리지 않도록 회차 시각을 확인한다. 보류 물건 키와 사유는 회차별 파이프라인 보고서 `errors`에 보존된다. 재개 시 현재 수집 자료에서 매칭을 다시 계산하므로 법원 상세·사진을 다시 수집할 필요가 없다. 접근 제한 중지 파일은 자동 해제하지 않는다. 최근 실행의 매칭 건수가 0이더라도 기존 DB 비교 자료가 삭제된 뜻은 아니며 화면은 이 경우 '기존 자료 유지'로 표시한다.

## 누락 자료 재확인 순회 · 2026-10-08

`./scripts/court/start-initial.ps1 -RepairPass`는 독립적인 `repair-checkpoint.json`으로 16개 법원 목록을 처음부터 대조한다. 기존 첫 순회의 체크포인트는 보존한다. 실제 사진 manifest에 있는 물건과 같은 날짜의 사진 없음 확인은 상세를 중복 조회하지 않는다. 목록의 가격·상태는 다시 저장한다. 페이지마다 `page-checked` 진행 신호를 남긴다. 회차 마지막에는 상세 신규 확보가 없어도 DB에 목록 변경을 반영한다.

`repair-seen.json`에 재확인한 물건을 보존하고 `repair-audit.json`에 상세 미확보, 사진 미확보, 이번 순회에서 미관측인 물건을 별도로 남긴다. 전 법원 순회 완료를 전체 자료 확보 완료로 표시하지 않는다. 미관측 자체는 매각·취하·취소 근거가 아니므로 별도 공식 검색·결과 검증 대상으로 유지한다. 국토부 접근 중지 파일과 오전 9시 예약 보류는 유지한다. 대표 사진 manifest 저장은 기존 현재 자료 저장과 같은 제한된 EPERM/EBUSY/EACCES 재시도를 사용한다. 관련 테스트 30개 통과.

## 미관측 물건 사건번호 재확인 · 2026-10-08

전체 목록 대조가 끝난 뒤 `node scripts/court/case-repair.mjs --limit=100000`으로 `repair-audit.json`의 미관측 물건과 상세 미확보 물건을 공식 경매사건검색에서 확인한다. 이번 회차 대상은 808개 물건이다. 같은 `running.lock`을 사용하며 기존 수집기와 동시에 실행하지 않는다. STOP과 공식 403/429·접근 제한을 존중한다. 국토부 접근 중지와 매일 오전9시 예약 PAUSED는 유지한다.

`case-repair-results.json`과 `case-proofs/`에 사건·물건 식별자와 공식 확인 결과를 체크포인트로 저장한다. 재실행은 확인 완료 건을 건너뛴다. 원래 목록의 가격·기일·lastSeenAt·관측 상태는 변경하지 않는다. 제공되는 상세 화면만 정확한 사건번호·물건번호를 검증해 기존 상세/사진 저장 구조에 반영하고, 신규 자료가 있으면 50건마다 및 회차 마지막에 DB를 반영한다. DB 오류와 matching 보류를 구분한다.

공식 상세 조회 버튼이 비활성인 경우 `detail-disabled`, 사건에 해당 물건번호가 제공되지 않으면 `property-not-provided`, 사건번호 형식이 잘못되면 `invalid-identifier`로 남긴다. 미제공 자체와 사건 전체 종국결과는 개별 물건의 매각·취하·취소 확정 근거가 아니다. `case-repair-audit.json`은 조회 완료와 상세·사진 확보 완료를 구분한다. 실제 첫 3개 물건의 순차 조회와 식별자 불일치 거부·목록 가격/시각 보존·접근성 설명문 오독 방지 테스트 5개 및 변경 파일 ESLint를 통과했다.

상세 화면의 이전 버튼은 사건 검색 결과로 돌아오지 않는 경우가 있어, 다음 물건에서 공식 사건 검색을 다시 열고 식별자를 재검증한다. 저장 결과는 화면 전환 전에 체크포인트에 남긴다. 재시작 시 DB의 최근 회차 이후 저장한 사건 상세가 있으면 반영을 이어간다. 서울서부 2025타경51193 물건1에서 신규 상세·대표 사진 1장을 확보하고 실제 `court_observations`/`property_media` 저장을 읽기 전용으로 검증했다. DB 반영 오류 0건, 국토부 매칭 보류 611건. 목록 lastSeenAt·가격은 보존했다.

## 최근 매각결과 추가 대조 · 2026-10-08

사건 재확인 완료 후 `node scripts/court/results-repair.mjs`로 기존 repair-audit 대상 808건만 공식 매각결과검색과 대조한다. 공식 화면은 매각기일 다음날부터 7일간 결과를 제공한다고 안내한다. 해당 기간 밖의 물건과 결과 미제공 물건의 종료를 추정하지 않는다. 상세 버튼 비활성을 우회하지 않으며 상세·사진 미확보 수치도 그대로 유지한다.

`results-repair-checkpoint.json`은 법원별 다음 페이지·관측 대상 키를 보존한다. `result-proofs/`에 공식 7셀 식별자 행과 3셀 결과 행을 저장한다. 기존 정확한 식별자·기일 검증을 사용하며 새 입찰일보다 과거인 결과는 반영하지 않는다. 매각·유찰 이외 결과는 unsupported 검토 항목으로 남긴다. 사건 검색의 공식 확인 근거도 기존 물건 payload에 보존하되 목록 가격·lastSeenAt을 바꾸지 않는다. 회차 종료 시 기존 파이프라인으로 DB에 반영하며 matching 보류를 DB 저장 오류와 구분한다. 공유 수집기 lock과 STOP, 공식 접근 제한, 국토부 보류, 오전9시 예약 PAUSED를 존중한다. 대상 범위·기일 보호·미지원 결과 검토·잘못된 표 거부 테스트 3개 및 변경 파일 lint를 통과했다.

수치 해석: 유효 대상 6,570건 중 상세 5,969건, 상세 미확보 601건이다. 601건 중 상세 버튼 비활성은 588건, 해당 물건 미제공은 13건이다. 사진이 있는 5,780건은 상세 확보 물건에 포함된다. 상세만 있고 사진이 없는 189건을 포함해 전체 사진 미확보는 790건이다. 형식이 잘못된 별도 2개 식별자는 위 유효 대상 집계에서 제외되며 검토 기록에 보존한다. 이 수치는 2026-10-08 사건 재확인 종료 직후 기준이다.
