# 프로덕션 비교 및 상세 화면 개선 — 2026-10-10

## 실행 중인 서버

- 개발: http://127.0.0.1:3000/dashboard?demo=0&source=court — 기존 PID 12428 유지.
- 프로덕션: http://127.0.0.1:3001/dashboard?demo=0&source=court — 새 PID 7516.
- 공매 비교: http://127.0.0.1:3001/dashboard?demo=0&source=onbid
- 찾기: http://127.0.0.1:3001/properties?demo=0&source=court

프로덕션은 `SITE_PERFORMANCE_BUILD=1`로 `.next-performance`에 빌드하고 같은 설정으로 `next start --hostname 127.0.0.1 --port 3001`을 실행했다. 로그의 Ready, 실제 명령줄, 3000·3001 포트 동시 Listen을 확인했다. Ready 1968ms는 서버 시작 시간이며 페이지 로딩 시간이 아니다. 로그와 프로세스 정보는 Git 제외 경로 `data/site-performance/`에 있다.

## 적용 내용

1. 카드에 IntersectionObserver를 연결했다. rootMargin 0으로 실제 화면에 들어온 카드에만 Link의 `prefetch=true`를 켜고, 화면 밖에서는 끈다. Next의 상세 미리 가져오기는 프로덕션에서 작동한다. 이전처럼 모든 카드의 prefetch를 끄지 않으며 화면 밖 카드 전체를 한꺼번에 미리 읽지도 않는다.
2. 공개 상세 DB 읽기에 60초 Next fetch 캐시를 적용했다. 익명·RLS 보호 읽기만 공유하고 사용자 쿠키나 비공개 원본을 캐시하지 않는다. 물건과 가격 이력도 병렬 조회한다. 상세 페이지의 `force-dynamic`을 제거하고 `revalidate=60`을 설정했다. query string 때문에 전체 페이지 ISR을 보장하는 설정은 아니며 실제 캐시는 공개 데이터 fetch에 적용된다. 온비드 비공개 원본 조회에는 이 공용 캐시를 적용하지 않았다.
3. 카드, 상세 대표 사진, 상세 사진 목록, 법원 증빙 사진의 `/media/court/*.webp`에 `unoptimized`를 적용했다. 원본 URL을 그대로 사용하며 원본 파일 자체는 수정하지 않았다.
4. 출처가 법원으로 이미 고정된 쿼리에서 반복하던 `source=onbid OR ...` 조건을 제거했다. 공매로 고정된 조회에서는 법원 주소 검사를 실행하지 않는다. 전체 출처 조회의 범위 제한은 유지한다.

`scripts/court/`, `data/court/`, 수집 프로세스, DB 구조/RLS는 변경하지 않았다. 배포·커밋·푸시는 하지 않았다.

## 인덱스 조사와 보류안

기존 인덱스에는 `last_seen_at`, 지역, 출처·물건관리번호와 사진의 property_id 등이 있다. 현재 목록 정렬인 `first_seen_at DESC NULLS LAST, id`를 직접 지원하는 인덱스는 없다.

읽기 전용 EXPLAIN ANALYZE에서 지역·출처·종료 제외와 이 정렬만 포함한 기본 24개 ID 조회는 24.136ms였고 정렬 전에 여러 행을 읽었다. 실제 공개 API의 사진·상태 임베딩, 정확한 count, RLS와 네트워크까지 포함한 시간과는 다르다. 따라서 기본 정렬 인덱스만으로 모든 지연이 사라진다고 판단하지 않았다.

추가 최적화 후보는 `(source, first_seen_at DESC NULLS LAST, id)` 인덱스다. 사진 정렬이 병목으로 확인되면 `(property_id, sort_order, id) INCLUDE (path)`도 따로 검토할 수 있다. **둘 다 만들지 않았다.** 운영 DB 구조를 변경하려면 사용자의 사전 승인을 받고 migration과 적용·롤백 절차를 준비한 후 실제 익명 API 전후 비교를 해야 한다. 현 시점에는 구조 변경 없이 제공되는 3001 화면을 먼저 비교할 수 있다.
